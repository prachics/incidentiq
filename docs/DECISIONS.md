# Decision log

Every non-obvious choice, why it was made, and what it would take to reverse.
Kept in build order. An interviewer who asks "why did you do X?" gets an answer
from here rather than a reconstruction.

---

## 1. Investigation state persists to Postgres, not process memory

**Date:** Phase 1

**Decision.** The agent's working state — extracted entities, retrieved
documents, tool call history, reasoning scratchpad, iteration counter — is
written to Postgres after every node transition, not held in a Python object
for the life of the request.

**Why.** An investigation is a long-running, multi-step process that can be
interrupted: the API restarts, a tool hangs, the human sits on an approval for
an hour. If state lives in memory, every one of those events loses the work.
Persisting it makes three things possible that are otherwise impossible:

- Resume after a crash from the last completed node
- Human-in-the-loop pauses that outlive the HTTP request that started them
- A queryable audit trail — "what did the agent know when it proposed that?"

**Cost.** A write per node transition, and state has to be JSON-serialisable,
which rules out holding live objects (open connections, model handles) in it.

**Reversal.** Swapping LangGraph's `PostgresSaver` for `MemorySaver` is a
one-line change, and everything still runs — it just loses the recovery
property. That the change *is* one line is the point: the interface is the
same, only the durability differs.

## 2. Three document tables, one shared chunk table

**Date:** Phase 1

**Decision.** `incidents`, `runbooks`, and `service_docs` each get their own
table with their own natural columns. All chunks from all three corpora live in
a single `chunks` table carrying `doc_type` and `parent_doc_id`.

**Why.** These two halves have different jobs. Documents are read by humans and
cited by the agent, so their schemas should reflect what they actually are — an
incident has a `root_cause` and a `resolution`; a runbook has neither. Chunks
are read only by the retriever, and the retriever wants exactly one indexed
table: one HNSW index, one GIN index, one query. Splitting chunks across three
tables would force a `UNION ALL` before ranking, which no index can serve well
and which makes reciprocal rank fusion awkward to express.

**Cost.** `parent_doc_id` is a foreign key by convention, not by constraint —
Postgres cannot reference three tables from one column. A deleted document can
orphan its chunks unless the delete path handles it.

**Reversal.** Cheap while the corpus is small; a re-chunk and re-embed is
minutes of compute.

## 3. Plain SQL migrations, applied by a 30-line script, instead of Alembic

**Date:** Phase 1

**Decision.** `db/migrations/*.sql` applied in filename order by
`scripts/migrate.py`, tracked in a `schema_migrations` ledger table.

**Why.** The interesting parts of this schema are things Alembic models poorly
and hides behind generated Python: the HNSW index and its `m` /
`ef_construction` parameters, the `GENERATED ALWAYS AS ... STORED` tsvector
column, and the append-only trigger on `audit_log`. Autogenerate would either
miss them or emit opaque `op.execute("...")` blocks — at which point you are
writing SQL anyway, with an extra abstraction on top.

**Cost.** No autogenerated diffs and no downgrade path. Every schema change is
a hand-written file.

**Reversal.** Adopting Alembic later means stamping the current schema as the
baseline revision. Straightforward, maybe an hour.

## 4. Local embeddings by default; the LLM provider is swappable

**Date:** Phase 1

**Decision.** Embeddings come from `BAAI/bge-small-en-v1.5` running locally via
`sentence-transformers` (384 dimensions). The LLM sits behind a provider
interface with three implementations: `ollama` (local, free), `anthropic`
(paid), and `stub` (deterministic, for tests).

**Why.** The two halves have very different cost profiles. Embedding the whole
corpus is a few thousand short forward passes — a local model does it in under
a minute on Apple Silicon, for free, as many times as chunk-size tuning
requires. Agentic reasoning is where model quality actually decides the outcome,
so that is where paying is worth it.

Keeping the LLM swappable also produces a genuinely interesting result: the
same 100 eval scenarios can be run against a local 14B model and a frontier
model, and the gap between them reported. That comparison is more informative
than either number alone.

**Cost.** `sentence-transformers` pulls in PyTorch, which is a large dependency
for what is ultimately one matrix multiply. Two provider interfaces to maintain.

**Reversal.** Changing `EMBEDDING_MODEL` requires changing the `vector(N)`
dimension in `002_corpora.sql` and re-embedding — the stored vectors are
model-specific and cannot be converted.

## 5. Retrieval relevance is labelled structurally, not by hand

**Date:** Phase 1

**Decision.** The ground truth for Recall@5 is generated alongside the corpus.
An incident counts as relevant to a query if it is the same failure archetype
*and* involves either the same service or one in its immediate dependency
neighbourhood. No human labels anything.

**Why.** Hand-labelling a retrieval set has a specific failure mode: you label
it after seeing what the retriever returns, and the labels drift toward
whatever the system already does. Structural labels are fixed before the
retriever exists, so the metric cannot be gamed — even accidentally.

It also scales. Adding a live situation adds its label set for free.

**Cost.** Structural relevance is a proxy for real relevance. A genuinely useful
incident from an unrelated service is scored as a miss, so the reported Recall@5
is a *lower* bound on real usefulness. That direction is the safe one, but it is
a real limitation and is stated in `docs/EVALS.md` rather than left to be found.

**Reversal.** A hand-labelled set can be added later as a second, smaller
evaluation and the two compared — which would itself be an interesting result.

## 6. Situations with no relevant history are kept, and flagged

**Date:** Phase 1

**Decision.** When corpus generation produces a live situation with zero
relevant historical incidents, it is kept and marked
`expect_no_useful_retrieval` rather than regenerated until it has matches.

**Why.** It was tempting to treat the first of these as a generation bug. It is
not — it is the most important test case in the suite. The worst failure mode
of a system like this is not being wrong; it is being *confidently* wrong about
an incident it has no information on. A system that scores well everywhere else
and fabricates here is worse than useless in production, because it is wrong in
exactly the situation where an engineer has no independent way to check it.

These situations are excluded from the Recall@5 average — recall is undefined
against an empty label set — and scored on abstention instead.

**Cost.** Two scoring paths instead of one, and the eval report has to explain
why the Recall@5 denominator is smaller than the scenario count.

## 7. Chunk 320 / overlap 64, chosen from a plateau rather than a peak

**Date:** Phase 2

**Decision.** Chunks of ~320 tokens with ~64 tokens of overlap, using recursive
character splitting that prefers paragraph boundaries, then sentences, then
lines, then words.

**Why.** Swept 96 → 640 tokens with overlap fixed at 20%. Everything from 192
upward scored identically (Recall@5 0.800); 96 and 128 were slightly worse
(0.783). The result is a **plateau, not a peak** — most documents in this corpus
are shorter than any of these budgets and are never split at all, so the
parameter only affects the longer runbooks.

Given a flat region, picking the argmax would be choosing between ties on noise.
The rule used instead is to take every setting within tolerance of the best and
choose the **middle** of that plateau. An edge setting is one corpus change away
from falling off; on a 12-situation labelled set that robustness is worth more
than a third decimal place.

**Cost.** The choice is only justified for *this* corpus. A corpus of long
postmortems would need re-sweeping, and the plateau would likely become a peak.

**Reversal.** One flag and a re-index: about two seconds of embedding.

## 8. Weighted RRF with `keyword_weight = 0.5`

**Date:** Phase 2

**Decision.** Fuse the vector and keyword rankings with reciprocal rank fusion at
the canonical `k = 60`, but weight the keyword ranker at 0.5 rather than 1.0.

**Why.** Plain RRF weights both rankers equally, which rewards *agreement* over
*confidence*. At k=60 a chunk ranked 10th by both rankers scores 2/70 = 0.029,
beating a chunk ranked 1st by one ranker alone at 1/61 = 0.016. When one ranker
is weaker than the other, its mediocre picks get promoted purely for being
seconded.

Measured: at weight 1.0, Recall@5 is 0.783; at 0.5 and 0.25 it is 0.800. `k`
itself made no measurable difference (5, 10, 20 and 60 scored identically), so
the canonical value is kept rather than tuned to noise.

**Cost.** One more parameter that is corpus-specific. The weight encodes "the
keyword ranker is somewhat weaker here", which is a property of this corpus, not
a universal truth.

**Reversal.** A keyword argument on `search()`.

## 9. Retrieval is measured twice: cold query and enriched query

**Date:** Phase 2

**Decision.** Every retrieval metric is reported under two conditions — the bare
user report, and the user report plus the error signatures a first
`get_service_logs` call returns.

**Why.** The first version of this evaluation used only the bare report. Those
numbers were bad (Recall@5 0.461) and the reason turned out to be a defect in the
measurement rather than the retriever: a query like *"something's wrong with
auth-service, customers are complaining, help?"* contains no information about
the failure mode, while relevance is defined *by* the failure mode. The eval was
scoring an impossible task.

The agent does not retrieve from that text. Its `retrieve` node runs after
`intake` has extracted entities and, on later loop iterations, after tools have
returned evidence. Enriched is the operating condition; cold is the floor.

Reporting both is more useful than replacing one with the other, because the gap
between them (0.461 → 0.800) is itself a result: it quantifies how much
retrieval improves *after* the first diagnostic call, which is the argument for
looping back to retrieval rather than running it once.

**Cost.** Every table has twice as many rows, and "Recall@5" is ambiguous unless
the condition is stated. It is stated everywhere.

## 10. Incidents quote their error signatures

**Date:** Phase 2 (migration `005`)

**Decision.** Incident records carry an `error_signatures` column holding the log
lines quoted in the write-up, and those lines are included in the embedded chunk
text.

**Why.** This began as a debugging result. Hybrid retrieval was performing at or
below vector-only in every configuration, which contradicted the expectation.
The cause was that the corpus contained no identifiers: `HikariPool`,
`OutOfMemoryError`, `x509`, and `NOT_ENOUGH_REPLICAS` appeared in `log_entries`
and **zero** times in the incident corpus. The keyword ranker had nothing
distinctive to match, so fusion could only dilute the vector ranking.

It was also simply unrealistic — a real postmortem quotes the error it was
diagnosed from.

After the change the keyword ranker scores 0.767 on its own, and fusion becomes
worthwhile. The wider lesson, which is the interview-relevant part: hybrid
retrieval is not universally better than dense retrieval. It is better when
documents contain tokens embeddings cannot represent. A corpus of pure prose
gains little from it.

**Cost.** A schema migration and a corpus regeneration. The eval numbers from
before this change are not comparable with those after it, which is why the
migration file records the earlier figures in a comment.
