# Decision log

Every non-obvious choice, why it was made, and what it would take to reverse.
Kept in build order. An interviewer who asks "why did you do X?" gets an answer
from here rather than a reconstruction.

---

## 1. Investigation state persists to Postgres, not process memory

**Date:** Phase 1

**Decision.** The agent's working state — extracted entities, retrieved
documents, tool call history, reasoning scratchpad, iteration counter — is
written to Postgres after every node transition, not held in a Python object
for the life of the request.

**Why.** An investigation is a long-running, multi-step process that can be
interrupted: the API restarts, a tool hangs, the human sits on an approval for
an hour. If state lives in memory, every one of those events loses the work.
Persisting it makes three things possible that are otherwise impossible:

- Resume after a crash from the last completed node
- Human-in-the-loop pauses that outlive the HTTP request that started them
- A queryable audit trail — "what did the agent know when it proposed that?"

**Cost.** A write per node transition, and state has to be JSON-serialisable,
which rules out holding live objects (open connections, model handles) in it.

**Reversal.** Swapping LangGraph's `PostgresSaver` for `MemorySaver` is a
one-line change, and everything still runs — it just loses the recovery
property. That the change *is* one line is the point: the interface is the
same, only the durability differs.

## 2. Three document tables, one shared chunk table

**Date:** Phase 1

**Decision.** `incidents`, `runbooks`, and `service_docs` each get their own
table with their own natural columns. All chunks from all three corpora live in
a single `chunks` table carrying `doc_type` and `parent_doc_id`.

**Why.** These two halves have different jobs. Documents are read by humans and
cited by the agent, so their schemas should reflect what they actually are — an
incident has a `root_cause` and a `resolution`; a runbook has neither. Chunks
are read only by the retriever, and the retriever wants exactly one indexed
table: one HNSW index, one GIN index, one query. Splitting chunks across three
tables would force a `UNION ALL` before ranking, which no index can serve well
and which makes reciprocal rank fusion awkward to express.

**Cost.** `parent_doc_id` is a foreign key by convention, not by constraint —
Postgres cannot reference three tables from one column. A deleted document can
orphan its chunks unless the delete path handles it.

**Reversal.** Cheap while the corpus is small; a re-chunk and re-embed is
minutes of compute.

## 3. Plain SQL migrations, applied by a 30-line script, instead of Alembic

**Date:** Phase 1

**Decision.** `db/migrations/*.sql` applied in filename order by
`scripts/migrate.py`, tracked in a `schema_migrations` ledger table.

**Why.** The interesting parts of this schema are things Alembic models poorly
and hides behind generated Python: the HNSW index and its `m` /
`ef_construction` parameters, the `GENERATED ALWAYS AS ... STORED` tsvector
column, and the append-only trigger on `audit_log`. Autogenerate would either
miss them or emit opaque `op.execute("...")` blocks — at which point you are
writing SQL anyway, with an extra abstraction on top.

**Cost.** No autogenerated diffs and no downgrade path. Every schema change is
a hand-written file.

**Reversal.** Adopting Alembic later means stamping the current schema as the
baseline revision. Straightforward, maybe an hour.

## 4. Local embeddings by default; the LLM provider is swappable

**Date:** Phase 1

**Decision.** Embeddings come from `BAAI/bge-small-en-v1.5` running locally via
`sentence-transformers` (384 dimensions). The LLM sits behind a provider
interface with three implementations: `ollama` (local, free), `anthropic`
(paid), and `stub` (deterministic, for tests).

**Why.** The two halves have very different cost profiles. Embedding the whole
corpus is a few thousand short forward passes — a local model does it in under
a minute on Apple Silicon, for free, as many times as chunk-size tuning
requires. Agentic reasoning is where model quality actually decides the outcome,
so that is where paying is worth it.

Keeping the LLM swappable also produces a genuinely interesting result: the
same 100 eval scenarios can be run against a local 14B model and a frontier
model, and the gap between them reported. That comparison is more informative
than either number alone.

**Cost.** `sentence-transformers` pulls in PyTorch, which is a large dependency
for what is ultimately one matrix multiply. Two provider interfaces to maintain.

**Reversal.** Changing `EMBEDDING_MODEL` requires changing the `vector(N)`
dimension in `002_corpora.sql` and re-embedding — the stored vectors are
model-specific and cannot be converted.

## 5. Retrieval relevance is labelled structurally, not by hand

**Date:** Phase 1

**Decision.** The ground truth for Recall@5 is generated alongside the corpus.
An incident counts as relevant to a query if it is the same failure archetype
*and* involves either the same service or one in its immediate dependency
neighbourhood. No human labels anything.

**Why.** Hand-labelling a retrieval set has a specific failure mode: you label
it after seeing what the retriever returns, and the labels drift toward
whatever the system already does. Structural labels are fixed before the
retriever exists, so the metric cannot be gamed — even accidentally.

It also scales. Adding a live situation adds its label set for free.

**Cost.** Structural relevance is a proxy for real relevance. A genuinely useful
incident from an unrelated service is scored as a miss, so the reported Recall@5
is a *lower* bound on real usefulness. That direction is the safe one, but it is
a real limitation and is stated in `docs/EVALS.md` rather than left to be found.

**Reversal.** A hand-labelled set can be added later as a second, smaller
evaluation and the two compared — which would itself be an interesting result.

## 6. Situations with no relevant history are kept, and flagged

**Date:** Phase 1

**Decision.** When corpus generation produces a live situation with zero
relevant historical incidents, it is kept and marked
`expect_no_useful_retrieval` rather than regenerated until it has matches.

**Why.** It was tempting to treat the first of these as a generation bug. It is
not — it is the most important test case in the suite. The worst failure mode
of a system like this is not being wrong; it is being *confidently* wrong about
an incident it has no information on. A system that scores well everywhere else
and fabricates here is worse than useless in production, because it is wrong in
exactly the situation where an engineer has no independent way to check it.

These situations are excluded from the Recall@5 average — recall is undefined
against an empty label set — and scored on abstention instead.

**Cost.** Two scoring paths instead of one, and the eval report has to explain
why the Recall@5 denominator is smaller than the scenario count.

## 7. Chunk 320 / overlap 64, chosen from a plateau rather than a peak

**Date:** Phase 2

**Decision.** Chunks of ~320 tokens with ~64 tokens of overlap, using recursive
character splitting that prefers paragraph boundaries, then sentences, then
lines, then words.

**Why.** Swept 96 → 640 tokens with overlap fixed at 20%. Everything from 192
upward scored identically (Recall@5 0.800); 96 and 128 were slightly worse
(0.783). The result is a **plateau, not a peak** — most documents in this corpus
are shorter than any of these budgets and are never split at all, so the
parameter only affects the longer runbooks.

Given a flat region, picking the argmax would be choosing between ties on noise.
The rule used instead is to take every setting within tolerance of the best and
choose the **middle** of that plateau. An edge setting is one corpus change away
from falling off; on a 12-situation labelled set that robustness is worth more
than a third decimal place.

**Cost.** The choice is only justified for *this* corpus. A corpus of long
postmortems would need re-sweeping, and the plateau would likely become a peak.

**Reversal.** One flag and a re-index: about two seconds of embedding.

## 8. Weighted RRF with `keyword_weight = 0.5`

**Date:** Phase 2

**Decision.** Fuse the vector and keyword rankings with reciprocal rank fusion at
the canonical `k = 60`, but weight the keyword ranker at 0.5 rather than 1.0.

**Why.** Plain RRF weights both rankers equally, which rewards *agreement* over
*confidence*. At k=60 a chunk ranked 10th by both rankers scores 2/70 = 0.029,
beating a chunk ranked 1st by one ranker alone at 1/61 = 0.016. When one ranker
is weaker than the other, its mediocre picks get promoted purely for being
seconded.

Measured: at weight 1.0, Recall@5 is 0.783; at 0.5 and 0.25 it is 0.800. `k`
itself made no measurable difference (5, 10, 20 and 60 scored identically), so
the canonical value is kept rather than tuned to noise.

**Cost.** One more parameter that is corpus-specific. The weight encodes "the
keyword ranker is somewhat weaker here", which is a property of this corpus, not
a universal truth.

**Reversal.** A keyword argument on `search()`.

## 9. Retrieval is measured twice: cold query and enriched query

**Date:** Phase 2

**Decision.** Every retrieval metric is reported under two conditions — the bare
user report, and the user report plus the error signatures a first
`get_service_logs` call returns.

**Why.** The first version of this evaluation used only the bare report. Those
numbers were bad (Recall@5 0.461) and the reason turned out to be a defect in the
measurement rather than the retriever: a query like *"something's wrong with
auth-service, customers are complaining, help?"* contains no information about
the failure mode, while relevance is defined *by* the failure mode. The eval was
scoring an impossible task.

The agent does not retrieve from that text. Its `retrieve` node runs after
`intake` has extracted entities and, on later loop iterations, after tools have
returned evidence. Enriched is the operating condition; cold is the floor.

Reporting both is more useful than replacing one with the other, because the gap
between them (0.461 → 0.800) is itself a result: it quantifies how much
retrieval improves *after* the first diagnostic call, which is the argument for
looping back to retrieval rather than running it once.

**Cost.** Every table has twice as many rows, and "Recall@5" is ambiguous unless
the condition is stated. It is stated everywhere.

## 10. Incidents quote their error signatures

**Date:** Phase 2 (migration `005`)

**Decision.** Incident records carry an `error_signatures` column holding the log
lines quoted in the write-up, and those lines are included in the embedded chunk
text.

**Why.** This began as a debugging result. Hybrid retrieval was performing at or
below vector-only in every configuration, which contradicted the expectation.
The cause was that the corpus contained no identifiers: `HikariPool`,
`OutOfMemoryError`, `x509`, and `NOT_ENOUGH_REPLICAS` appeared in `log_entries`
and **zero** times in the incident corpus. The keyword ranker had nothing
distinctive to match, so fusion could only dilute the vector ranking.

It was also simply unrealistic — a real postmortem quotes the error it was
diagnosed from.

After the change the keyword ranker scores 0.767 on its own, and fusion becomes
worthwhile. The wider lesson, which is the interview-relevant part: hybrid
retrieval is not universally better than dense retrieval. It is better when
documents contain tokens embeddings cannot represent. A corpus of pure prose
gains little from it.

**Cost.** A schema migration and a corpus regeneration. The eval numbers from
before this change are not comparable with those after it, which is why the
migration file records the earlier figures in a comment.

## 11. The LLM sits behind an interface with a deterministic stub as a first-class implementation

**Date:** Phase 3

**Decision.** Three providers — Anthropic, Ollama, and a scripted stub. The stub
is not a test fixture bolted on afterwards; it is the implementation almost all
tests run against.

**Why.** The structural properties of the graph — does the loop terminate, does
state survive a crash, does a rejection re-enter planning, can an unapproved
action execute — have nothing to do with model quality. Testing them against a
real model would make those tests slow, costly and non-deterministic, so they
would be run rarely and trusted less. Against the stub they run in seconds and
never flake.

The second benefit was not the motivation but turned out to matter more: the
same 100 scenarios can run against a local 14B model and a frontier model, and
the gap between them reported. That comparison says more than either number.

**Cost.** Two provider implementations to keep in step, and a stub whose
behaviour has to stay realistic enough to exercise the real control flow rather
than short-circuiting to a canned answer.

## 12. Retry policy is classified by error kind, not applied uniformly

**Date:** Phase 3

**Decision.** `timeout` and `failed` are retried; `malformed` is not. Argument
errors — unknown service, unknown metric, a version never deployed — are
classified `malformed`.

**Why.** This began as a bug. An unknown service name was classified as a
transient failure, so the retry loop tried identical bad arguments three times
per iteration and burned the entire budget without one successful tool call.
Retrying an argument error cannot succeed by definition.

Breaking the loop and returning a *specific* message is worth more than the
retry was: unknown service names are matched with trigram similarity, so the
model receives "unknown service 'checkout-svc'. Did you mean: checkout-service?"
and corrects on the next iteration.

**Cost.** A tool author has to choose the right status. A genuinely transient
failure misclassified as `malformed` would not be retried.

## 13. Structured output is constrained by JSON Schema, not requested in the prompt

**Date:** Phase 3

**Decision.** Each reasoning node declares a Pydantic model; its JSON Schema is
passed to the sampler for grammar-constrained decoding, and every field is
required with empty-string sentinels instead of nullable types.

**Why.** Three escalating findings, each from observed behaviour:

1. "Return exactly this JSON shape" in a prompt is a request. The local model
   honoured it at small context and degraded as prompts grew, until five of
   seven planning calls were unparseable.
2. Ollama's `format: "json"` fixed *syntax* but not *structure*. Past ~3000
   prompt tokens the model returned valid JSON with an invented schema —
   `{"incident_updates": ...}` where `root_cause` was expected. Parsing
   succeeded, every field read back `None`, and the agent emitted an empty
   proposal **having reasoned its way to the correct answer**. A silent failure
   at the last step.
3. Passing the schema constrained the field names, and the grammar still let the
   model omit `root_cause` entirely, because Pydantic marks a field required
   only when it has no default. Every field is now required — which forced
   dropping nullable types, since a field can only be required if it has a
   representable way to say "nothing here".

**Cost.** Empty string means "absent", so nodes translate sentinels back to
`None`. Schemas must stay simple enough for llama.cpp's grammar compiler, which
falls back to unconstrained output *silently* on a schema it cannot convert.

## 14. Tool selection is validated by category, not just existence

**Date:** Phase 3

**Decision.** A proposed remediation must be a registered tool **and** a write
tool. Read-only tools are rejected as firmly as hallucinated ones.

**Why.** The model proposed `get_service_logs` as a remediation. It is a real
registered tool, so an existence check passed — and it would have opened an
approval request asking a human to authorise an action that changes nothing.

The general lesson is worth more than the fix: validating that a name resolves
is not the same as validating that the thing it resolves to belongs in this
position.

**Cost.** None material.

## 15. Eval ground truth is the archetype, not the narrative

**Date:** Phase 3

**Decision.** Scenarios grade the agent's diagnosis against keywords pooled from
**every** root-cause variant of the expected archetype, requiring two absolute
matches rather than a proportion.

**Why.** The first real eval run reported a scenario as "named the service but
not the mechanism (0/5 keywords)". The agent was right and the grader was wrong.
Each archetype has two narratives for the same failure — `disk_full` is either
WAL segments accumulating or autovacuum falling behind. The corpus contains
both. The generator drew one and graded against that sentence alone; the agent
diagnosed disk exhaustion on the correct service and described the other. The
same answer scores 6 hits under the pooled vocabulary.

The archetype is determinate; the narrative is not. Grading should only depend
on what is determinate.

**Cost.** A broader vocabulary risks accepting a wrong answer, so a test asserts
that an unrelated diagnosis (TLS expiry against `disk_full`) still fails. A
vocabulary broad enough to accept anything would be a worse bug than the one
being fixed.

## 16. Local inference speed is treated as a design constraint, not an inconvenience

**Date:** Phase 3

**Decision.** The harness has `--sample` (stratified across scenario kinds) and
`--max-iterations`, and any iteration cap is written into the results file.

**Why.** qwen2.5:14b generates at ~24 tok/s on an M4 Pro. Prompts run ~3000
tokens, of which retrieved documents are 45%. An investigation is 10-12 LLM
calls, so ~2 minutes; approval scenarios that interrupt and resume are longer.
The full 100-scenario suite is an overnight job.

That changes how the project is developed rather than being a footnote.
`--limit` was not enough because it takes the first N, which would run only one
category — hence stratified sampling. And a capped run is not comparable with an
uncapped one, so the cap is part of the output rather than something someone has
to remember mentioning.

**Cost.** Capped runs understate task completion. The generated report says so
explicitly.

## 17. The approval id is the idempotency key

**Date:** Phase 4

**Decision.** Every request that executes an approved action carries
`Idempotency-Key: <approval id>`. The control plane applies the first request
per key and replays its stored response to every later one.

**Why.** One approval authorises one execution, and a key per approval says
exactly that. A random key per request would protect a single HTTP retry but
not the other duplicate: `act` running again after a crash, which builds a new
request. A key derived from the approval is the same in both cases, so the
guarantee does not depend on which code path repeats the call.

**Cost.** An approver who wants the same action applied twice needs two
approvals. That is the intended behaviour, not a limitation.

**Reversal.** The key is computed in one place, `execute_action`.

## 18. The approver's identity comes from the API key

**Date:** Phase 4

**Decision.** API keys map to a user and a role (`viewer`, `approver`).
`decided_by` is the user behind the key that made the request. There is no
`decided_by` field in the request body.

**Why.** An approval record is only worth something if "who approved this?"
has a trustworthy answer. A body field lets any caller write any name.

**Cost.** Static keys in configuration, no rotation or SSO. The routes depend
only on a `Principal(user, role)`, so putting a real identity provider in front
changes the authentication function and nothing else.

## 19. A decision is a conditional UPDATE, not a read followed by a write

**Date:** Phase 4

**Decision.** `UPDATE approvals SET decision = … WHERE id = … AND decision IS NULL
RETURNING …`. No row back means someone else decided first: 409.

**Why.** Reading "is it pending?" and then writing lets two concurrent requests
both see pending and both write; the second silently overwrites the first, and
the graph is resumed twice. The conditional update makes the check and the
write one atomic step. Tested with five concurrent approvers: one 202, four 409,
one resume.

## 20. The control plane is a mock behind a real HTTP contract

**Date:** Phase 4

**Decision.** Approved actions go through an HTTP client to a mock control plane.
By default it runs in-process through an httpx transport; in the compose stack
it is its own container, set by `CONTROL_PLANE_URL`.

**Why.** Restarting real services adds nothing to the engineering here. What
matters is the failure behaviour of a remote call - refused, applied but
unanswered, slow - and a direct function call cannot fail that way. Keeping the
client identical in both modes means the tests exercise the same retry and
idempotency code that crosses the network in the container setup.

**Cost.** The mock's fault injection is seeded per (key, request number), so it
is reproducible but simpler than a real network. A lost response becomes a read
timeout in-process and a 504 over HTTP.

**Reversal.** Point `CONTROL_PLANE_URL` at anything that implements
`POST /v1/operations` with idempotency keys.

## 21. OpenTelemetry for tracing, not the Langfuse SDK

**Date:** Phase 6

**Decision.** Traces are OpenTelemetry, exported over OTLP to Jaeger in the
compose stack. The Langfuse container, provisioned in Phase 1 but never
instrumented, is removed.

**Why.** The interesting trace in this system is not only the LLM calls. It is
the API request, the worker job, the graph nodes, the tool attempts, and the
request to the control plane, which runs in another process. OpenTelemetry
covers all of them with one trace id and propagates across HTTP by standard
headers; an LLM-specific SDK would see the model calls and little else. LLM spans
still carry the GenAI semantic-convention attributes that LLM observability tools
read, so any OTLP backend that understands them can display them.

**Cost.** Jaeger shows spans, not prompt-level views or eval scoring; those stay
in the evaluation harness.

**Reversal.** Point `OTEL_EXPORTER_OTLP_ENDPOINT` at any OTLP backend, Langfuse
included.

## 22. The MCP server exposes only the read-only tools

**Date:** Phase 7

**Decision.** `python -m incidentiq.mcp_server` serves the diagnostic tools over
MCP. Tools with `requires_approval` are neither listed nor callable, and every
call runs on a connection with `default_transaction_read_only=on`.

**Why.** A write tool in IncidentIQ is safe because of the path around it: a
proposal, a person's approval, one execution through the control plane, an audit
record. An MCP client calling `restart_service` directly would skip all of it.
Filtering on `requires_approval` means a write tool added later is excluded by the
same flag that already sends it to approval; the read-only session means a
"diagnostic" tool that writes by mistake fails in Postgres instead of succeeding
quietly. Failure injection is off because it exists to test the agent's recovery,
not to hand a person wrong answers.

**Cost.** An MCP client can diagnose but not remediate; to act, it has to go
through the approval API like everyone else.

**Reversal.** Exposing writes would mean an MCP tool that *proposes* an action
into the approval queue, not one that executes it.

## 23. Langfuse reads the OpenTelemetry traces; no Langfuse SDK

**Date:** Phase 7

**Decision.** Traces can go to Langfuse through its OTLP endpoint, with the auth
header in `OTEL_EXPORTER_OTLP_HEADERS`. Nothing Langfuse-specific is in the code:
LLM spans already carry the GenAI attributes Langfuse turns into generations, and
the job span's `session.id` is the attribute its Sessions view groups by. Retrieval
got a span of its own, which helps in Jaeger as much as in Langfuse.

**Why.** Decision 21 holds: the trace that matters spans the request, the worker,
the graph and the control plane, and only OpenTelemetry covers all of it. Langfuse
adds the LLM-centred views (generations, token counts per call, sessions) on top of
the same spans, so it is a second backend, not a second instrumentation.

**Cost.** Prompts and completions are not on the spans, so Langfuse shows each
call's model, tokens and latency but not its text. Adding them would put incident
data in every trace backend; they stay in the stored investigation state.

**Reversal.** Unset the two variables, or point them at another OTLP backend.
